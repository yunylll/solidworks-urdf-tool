# SolidWorks 2026 と元アドインのコード呼び出し：実現性の検証結果

[English](FEASIBILITY.md) | [简体中文](FEASIBILITY.zh-CN.md) | **日本語**

日付：2026-10-07（Asia/Shanghai）。結論：**実現可能。動作するブリッジ適合の試作版を作成し、実際の MCP エクスポートで検証しました。**

今回呼び出したのは、このマシンにインストールされている SW2URDF.dll の元のエクスポートコードです。モデルの読み込み、質量/慣性の計算、STL のエクスポートには SolidWorks が実際に動作して関与しました。模擬データではなく、computer-use も使っていません。

試作版の総質量は **0.3452524549775949 kg** で、SolidWorks が報告するネイティブの全体質量との差は **6.106226635438361e-16 kg** でした。

繰り返しテストでは、URDF の数値を 1e-12、メッシュ座標を 1e-8 m まで比較しました。2 回の出力はバイト単位では完全に同一ではなく、ごくわずかな浮動小数点の差があります。ここでいう「結果が一致」を、バイト単位で同一という意味に解釈してはいけません。

## 実際のエクスポートの証拠

MCP 統合の生レポート、ジョブのディレクトリ、エクスポートされたファイルにはローカルのパスが含まれるため、リポジトリには含めていません。README の手順でローカルに再生成できます。

## 解決した問題

1. 通常の COM アクティベーションはユーザーのセッションを再利用することがあります。ブリッジは新しいプロセスを明示的に起動し、PID で ROT オブジェクトを探し、COM の初期化完了を待ちます。
2. 元アドインはエクスポート先ディレクトリを作成するときにメッセージボックスを表示します。公開されている IMessageBox の拡張ポイントを通じて、その内容をログに書き出すようにしました。
3. 設定をデシリアライズしただけでは、実行時のコンポーネント参照は復元されません。LoadSWComponents を追加し、永続参照がない場合はエラーにします。
4. コンポーネント参照を復元しなかった初回のラウンドでは、空の STL と全体質量の二重計上が発生しました。このラウンドは無効と判定し、最終検証は修正後の独立したジョブで行っています。
5. STL の偏差は、粗い/細かいモードでアクティブモデルのサイズから自動計算されることがあります。設定の比較は同じモデルのコンテキストで行う必要があり、空のセッションと開いたモデルの導出された偏差値を比較してはいけません。
6. MCP SDK は構造化された戻り値に明示的な dict[str, Any] 型を必要とします。ツールの出力構造と、ローカルの中国語パスのエンコーディングを修正しました。

## 検証の範囲と提案

**ここで完了したのは、実現性の検証とブリッジ適合の試作版です。** 元アドインの DLL は元の 1.6.1 系のままで、すべての SolidWorks 2026 モデルを完全にサポートすると謳う新しいインストーラは公開していません。

現在のエクスポートツールが受け付けるのは、ワークスペース内にあり、旧アドインの URDF 設定が保存されていて、CAD の参照が単一のディレクトリにまとまっているアセンブリです。次の項目は未検証です。

- 数百コンポーネント規模の実ロボットの完全なエクスポートと、ディレクトリをまたぐ依存関係のパッケージ化。
- prismatic と revolute のリミット、mimic、フレキシブル/複雑な入れ子のサブアセンブリに対するカバレッジテスト。
- 旧設定のないモデルでの、コードによるツリー構築、パラメータ設定、ジョイントの自動推定。
- カスタム STL 精度モードでのエクスポートと復元の一連の流れ。現時点では、ユーザーの元のカスタムモードが変化していないことを読み取り専用で確認したのみ。
- ROS 2、Gazebo、MuJoCo などのターゲット環境での動作検証。元アドインが生成するのは従来型の ROS パッケージです。
- 残っているエラーダイアログの完全な除去。ディレクトリのプロンプトは対処済みで、そのほかのエラーダイアログはタイムアウトによる失敗として返し、独立プロセスをクリーンアップします。

MCP サービスは実際のローカルクライアントから呼び出し済みですが、現在のチャットのツール一覧にはまだ登録されていません。ワークスペースには、stdio クライアントが読み込める起動パラメータを用意してあります。

次の段階では、このブリッジ構成を維持したまま、元アドインに正式なヘッドレスのエクスポートインターフェース、構造化された設定、エラーの返却を追加し、実ロボットモデルの独立した Pack and Go コピーで検証することをお勧めします。現在の根拠は、「2026 への適合 + 低レベルのコード/MCP 経由の呼び出し」という方針が成り立つことを確認するには十分ですが、すべてのアセンブリに互換性があると主張することはできません。
